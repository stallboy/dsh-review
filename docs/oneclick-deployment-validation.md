## 环境与方法

本机为 Windows，Node.js 24.x；使用实际 `pack:central`、`pack:plugin` 安装包、隔离临时目录、SQLite 和本地 Git 仓库验证。源码和被测部署目录分离，不使用真实业务账号、Token 或仓库。

最初 5 项部署测试因实现缺失全部失败，随后实现脚本并补齐平台入口与目录占用用例，7 项部署测试全部通过。后来将中央启动收紧为从包含中文、空格和 `&` 的部署路径调用原生 `start.cmd`，不再只调用内部 Node 脚本。

部署测试验证：

1. 部署、启动使用不同入口；启动拒绝 `--git`；低于 Node 24 被拒绝。
2. Windows 程序目录被进程短暂占用后，替换仍可完成；重试次数有限。
3. Windows 原生入口与 Git Bash 下四个 POSIX 入口能调用正确脚本并返回退出状态。
4. 中央重复部署移除旧版多余文件，保留数据、端口、账号；从部署目录独立启动，健康检查、页面和登录可用；运行中拒绝再次部署或启动。
5. 无效安装包失败后，旧程序与配置保留；数据与程序重叠、源码目录作为目标时拒绝。
6. 节点重复部署保留连接配置原字节及执行记录；轻量 DSH 进程夹具确认启动继承 `DSH_HOME` 和 Token 环境，部署配置不存 Token。
7. 沿用节点配置时，旧工作副本位于 `app` 的情况也必须在安装前被拒绝；原业务文件及两份配置保持不变。
8. 两次真实 Git 提交分别生成不同版本，`--git` 二次部署获得新产物与最新提交号。
9. 在读取配置与获取锁的调度窗口模拟一次部署更新，启动使用锁内最新配置。
10. 在最终发布配置时注入文件重命名失败，旧 app、全部五个启动文件及部署配置完整恢复，并释放操作锁。

所有原有测试和断言保留；新增测试没有通过删除或放宽原有断言获取通过。

## 审查与复核

独立 reviewer 在不继承实现会话上下文的情况下只读审查代码、文档与测试；主任务再逐条复核。

- 已确认并修复：节点沿用已有工作副本时漏做目录重叠校验。先用真实插件包复现覆盖成功返回 0 的错误；修复后对全部现有和新增工作副本统一校验。回归使用不存在的安装包仍先获得路径重叠拒绝，证明检查发生在安装之前。
- 已确认并修复：启动在锁外读取旧配置。调度窗口回归先观察到 `old-configuration`，修复后使用最新配置。
- 已确认并修复：发布失败时只回退 app，遗漏启动文件。启动文件改为完整暂存备份并参与发布/恢复；故障注入回归先复现文件变化，修复后逐字节恢复全部文件。恢复本身失败时保留备份并报告路径。
- 已确认并修复：Git 模式仍复制调用端的旧启动文件。现在从新克隆源码获取启动文件，两次 Git 提交用独立启动版本标记验证同步更新。
- 最终只读复审通过，原 1 项 P1、3 项 P2 均已闭环，无未决 P1/P2。Reviewer 独立运行锁内配置读取及既有工作副本防覆盖两项轻量回归；主任务确认发布回退和 Git 更新三项回归全部通过，再执行最终全量验证。

## 验证边界

Windows 与 Git Bash 的结果不能替代 Linux/macOS 原生验证。三平台 CI 已配置，本次尚未推送或触发远端运行，不声称 Ubuntu/macOS 已通过。

节点自动测试使用真实插件包与轻量启动夹具，没有在真实 DSH 中自动启用插件或调用模型。首次插件启用、实际 DSH 运行时、跨机器 HTTPS、真实模型及各项目工具链需按使用说明在目标环境验收。

脚本不提供数据库跨版本回滚或降级保证。升级前仍须备份中央数据、节点执行记录和业务工作副本，处理未决任务；部署目录内的数据保护不能替代备份。
