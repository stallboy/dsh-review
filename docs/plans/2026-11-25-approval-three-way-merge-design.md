# 固定候选基线与逐项审批合并设计

> **任务来源**: 用户确认各候选从固定审查基线生成，批准时通过 Git 三方合并计算结果，再逐项交付到原生 Git 或 SVN。
> **任务内容**: 定义三方合并的输入、沿用批准的条件、冲突处置与交付边界。
> **参考文档**:
> - `SPEC.md` §3.2、§7.5、§7.7、§16.7 — 候选正交性、审批事务和原生交付。
> - `docs/2026-11-25-svn-approval-patch-conflict.md` — SVN 退出码为零时的部分应用缺口。
> - `https://git-scm.com/docs/git-merge` — 三方合并及冲突处理。
> **生成日期**: 2026-11-25

**状态**：已在独立实施工作副本接入。用户仍按现有入口逐项批准。

## 审批如何计算交付内容

1. 一轮审查开始时固定业务快照。每个初始候选独立基于这一快照生成。候选修复或 Rebase 后，审批使用当前版本自己的 `base_revision`。Git 基线定位到提交，SVN 基线定位到仓库身份、目标路径及 revision。
2. 批准任务取得工作副本锁，核验候选和发现的审批条件，按配置同步原生目标，再检查原生严格应用能否完整落地。可以完整应用时继续走原生路径。
3. 遇到文本上下文失配且具备核验条件时，读取候选来源和待交付目标，将补丁完整应用到来源以得到候选快照。以来源作为共同祖先，在临时 Git 环境中合并候选快照和目标快照。已提交的其他候选和团队改动由目标快照带入。临时环境只服务本次审批，待交付差异以当前目标为起点。
4. Host 验证待交付差异与已审修改一一对应。验证通过后，再确认原生目标未变，写入正式工作区并运行门禁。通过现有原子提交写入业务内容、审批记录及补丁删除。中央模式继续使用现有的远端交付和结果核验规则。

例如 A 修改第 5 行、B 修改第 7 行。先批准 A 后，B 的合并输入分别是审查时的文件、含 B 的文件和含 A 的当前文件。如果最终相对当前文件只加入 B 的原修改，就继续交付 B。A、B 可交换批准顺序。若 A、B 改的是同一个业务判断，就由冲突处置和门禁确定下一步。同一发现的多个备选仍按发现互斥规则执行。

## 何时沿用批准

- 首期支持已有普通文本文件上的内容修改。按路径比较带位置的字节级增删序列，利用来源到目标的对应关系定位原修改。行号变化、修改区间外的上下文变化允许通过。新增、删除、重命名、模式变更、二进制和 SVN 原生属性等超出范围的变更继续使用原生严格应用。
- 保留旧候选、浅克隆和 SVN-only 环境中可完整应用的原生审批。需要三方合并时必须验证来源和目标，缺少历史或工具时报告具体原因，无须因此自动拉取历史或安装 Git。已确认的绑定不匹配必须停止审批。
- 路径、修改位置或内容无法唯一对应时需要复审。典型情形包括重复文本歧义、候选只有部分修改还需要应用、整份修改已生效、合并派生额外修改。文本冲突与等价性核验失败均进入 `PATCH_CONFLICT`。Agent 从干净的目标基线生成新版本，交由人员重新批准。来源或目标快照不可核验时按 §7.5 停止审批并报告原因。
- 门禁在含待交付改动的原生目标工作区执行，覆盖候选与已有代码叠加后的行为。门禁后继续核对候选 guard、业务内容、模式、删除集合和额外改动。提交撞车按既有规则重新取基线和计算。提交结果不明时保留待核验状态。

## 设计取舍

逐项原生交付能保留现有审批、交付和恢复单位。临时 Git 环境增加快照和合并成本，首期将范围限制在可核验的文本修改。持久的审查合并分支更适合明确要求整批生效的流程，会额外引入分支维护、积压和远端漂移。需要一起生效的修复可按现有规则生成一个组合候选。
