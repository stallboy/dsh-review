# Harness 审查与问题级评审改造方案

> **任务来源**: 本聊天先审查了项目提示词与实际执行链路，随后用户逐项确认新的审查、修复、权限、问题记录与失败处理设计，并要求对照 SPEC 和实现、复审方案、实施、复审及测试。
> **任务内容**: 恢复完整 Harness Agent Loop；审查与人工审核后的修复分离；每个问题一份跨轮复用的 review.md；同目录保留递增补丁和最多两个有效方案；完成审批、界面、协议及恢复语义改造。

## 目标、架构与技术

**目标**: 审查 Agent 自主读取项目并交付未经应用的方案；人审后程序应用，保持问题记录、权限和恢复行为可核验。

**架构**: 复用总调度、审查租约、原子提交、Git/SVN 适配和现有前端。Host 启动完整 Harness 并核对结果，不再提前枚举和裁剪待审源码。新增问题级 review schema，作为新问题唯一可编辑事实；旧 v1/v2 继续读取，新格式不向旧档案或处置 YAML 重复写事实。

**技术**: TypeScript、Node.js 24、现有 DSH 会话控制与 Codex/Claude CLI、Git/SVN、现有原生测试、现有两端界面。

**执行方式**: 按 `writing-plans` 与 `executing-plans` 的检查点实施；用户已明确授权自审后实施，不再重复请求开工批准。独立审查按仓库 AGENTS 执行。

## 已确认的需求

1. 总调度、初审、逐条独立复核与方案 Agent 保留各自上下文，全部在同一项目 cwd 运行。审查时不并行开展其他独立工作。
2. 允许通过 Harness 读取项目任意内容。默认写入 `.ai-review`；必要取证可以临时写到项目其他位置，结束后归档材料并恢复业务工作目录。
3. 审查阶段不应用业务补丁，不通过应用补丁来验证修复效果。可以验证问题和检查补丁格式、基线及可应用性。
4. 明确问题交付置信度最高的一个或两个互斥完整方案；重大改动可以只交付可复制给外部执行人的文字方案。
5. 每个问题一个稳定 ID、一份 review.md。后续审查更新同一文件并保留人工记录及历史。审查档案只记录本轮观察索引、覆盖与运行事实。
6. 同目录补丁从 001.patch 递增且不覆盖。方案身份和当前补丁另行记录，有效方案最多两个，历史补丁不计入上限。
7. 人审绑定选中的方案、补丁、问题版本和内容。程序先应用；应用失败时允许 Agent 辅助，分支合并时给出完整工具权限。改变业务行为、范围或方案须产生新提案并重新人审。
8. 补丁应用后验证失败，不启动 Agent 修正。先恢复本次业务改动，再记录失败和恢复结果，问题进入待人工处理；恢复或提交结果不明时保留现场和恢复状态。
9. 应用成功且验证通过直接解决问题，不追加复核。下轮再次发现同一问题时沿原记录重开。
10. 外部人工接手、反馈完成与复核解决分别记录；反馈完成后由后续审查以代码证据确认关闭。

## 差异清单

以“需要独立实现并验收的行为”为一组，共 17 组实质差异；同组的 SPEC、Host、协议和 UI 修改合并计数，不按文件凑数。

| 编号 | 当前 SPEC / 实现 | 新契约与改造范围 |
| --- | --- | --- |
| D01 | 阶段禁用本地工具并拒绝工具事件 | 完整 Harness Loop；`audit-stage-runner.ts` |
| D02 | 阶段 cwd 为临时目录，补丁在专用副本落地 | 全阶段共用项目 cwd，运行文件独立于 cwd |
| D03 | 32 KiB 单文件、96 KiB 总量和 48 文件视图 | 删除审查输入裁剪；只在结果证据核验时回读指定位置 |
| D04 | 审查范围也限制源码读取 | 全项目可读，范围仅约束正式发现和提案目标 |
| D05 | 方案返回 before/after，由 Host 修改代码 | Agent 直接交付 patch 和方案文件，Host 不生成业务编辑 |
| D06 | 审查生成与收尾会应用补丁并跑修复门禁 | 审查仅检查；实际应用及修复验证移至人工审核之后 |
| D07 | 审查业务目录保护依赖移除工具和临时副本 | 阶段权限、取证路径、前后工作区检查和材料归档 |
| D08 | review.md 强制存在当前 patch | 新问题格式允许纯文字、零补丁 |
| D09 | 同一 finding 的方案分散到多个候选目录，最多三个 | 同一问题目录内最多两个有效方案 |
| D10 | 版本号、补丁号与当前方案混为一体 | 保留递增补丁账本，显式选择稳定方案及其当前补丁 |
| D11 | 当前问题事实由 audit.items、候选、处置 YAML 共同投影 | 新 schema 的问题 review.md 为唯一事实源，旧格式兼容读取 |
| D12 | 每轮主要新增候选，不允许更新既有候选或保存证据子目录 | 校验本轮涉及文件及不可变历史，跨轮沿用原问题路径 |
| D13 | 批准会删除历史 patch，业务提交派生依赖删除事件 | 新问题保留全部 patch，提交定位验证实际批准记录与业务变化 |
| D14 | 门禁失败可自动调用 AI 修正，未保存问题失败状态 | 还原、记录、待人工，禁止该分支调用修复 Agent |
| D15 | 外部接手只能补线索，没有明确的完成反馈状态 | 记录外部完成、待复核及有证据的后续关闭 |
| D16 | 两端 UI、中央 payload 和能力协商依赖独立候选 ID | 显式问题/方案/补丁选择、新状态展示和新格式能力协商 |
| D17 | 完整工具事件流也受最终 JSON 的 1 MiB 限额限制 | 流式处理工具事件，最终结构化结果另行限额 |

继续保留且强化的既有行为：独立复核后才报告确定发现、实际影响定级、固定基线、并发守卫、批准门禁、实质方案变化回人审、提交成功/已证明失败/结果不明三分支、默认不 push 和不发布。

## 实施顺序与验收

### 任务 1：契约和基线

- 在当前独立 worktree 创建任务分支与 `.dsh/task-brief.md`；以 `dad46a2` 为实现基线，保留其一小时阶段时限修复。
- 更新 SPEC 的 §3、§4、§5、§7.4–7.6、§10–11、§13–14 及中央能力说明。新格式与旧格式的适用边界必须明确。
- 先跑现有 typecheck、build、全量测试，记录数量及环境失败，不能把环境错误改成测试跳过。

### 任务 2：问题级 schema 和单一事实源

- 修改 `packages/protocol/src/review.ts`、`frontmatter.ts`、`invariants.ts`、`store.ts`，新增专门的问题字段校验模块。
- 新 schema 支持稳定 finding ID、零到两个方案、递增完整补丁账本、观察、处置及失败记录；不覆盖旧字段和未知键。
- `record_revision` 为问题记录版本，初始为 1，纯文字问题同样为 1；API currentRevision 是兼容映射。`patches[].id` 是独立的目录补丁编号，不能用问题版本定位当前补丁。评论绑定记录版本，方案通过 current_patch 指向账本项。
- 旧 v1/v2 的强校验保留。新记录出现后，旧同 finding 仅作为历史，不再竞争当前状态。
- 验收：零补丁文字问题、两备选、001/002/003 修订、旧格式回读、非法交叉引用与重复问题 ID 拒绝。

### 任务 3：完整 Harness 执行与审查权限

- 修改 `audit-stage-runner.ts`、`audit-stages.ts` 和阶段模板，将项目 cwd 与运行产物位置分离。
- 删除 `sources()` 容量视图和工具事件黑名单；保留基线、租约、阶段串行、超时、认证失败与进程树停止核验。
- 使用实际 Harness 的文件权限能力，必要时复用可信外层 sandbox；不能把提示词约束称作 OS 隔离。验证临时取证的授予、归档与恢复边界。
- 验收：真实工具读取未预注入的大文件、跨范围读取调用方、默认允许审查目录写入、拒绝或准确报告非授权写入、同一 cwd、独立上下文和停止状态。

### 任务 4：审查提案、发布与跨轮更新

- 修改 `audit-stage-artifacts.ts`、`api-audit.ts`、`auditor.ts`、`audit-history.ts` 及模板。
- 方案阶段直接读取 Agent 生成的 patch/材料，检查格式、路径、基线及 dry-run 可应用性。不得实际应用或调用修复门禁，包括 finalize 路径。
- 新问题与文字方案都写 review.md；既有问题只追加允许的新观察和方案修订。核对人工记录、历史 patch 和共享基线，拒绝覆盖与未登记文件。
- SVN 提供真正不写业务源码的 dry-run 检查，复用严格 hunk 结果判定，但不得调用后续实际应用；单独覆盖 skipped/rejected hunk。
- 审查档案保持索引与覆盖，不建立新问题第二套可编辑事实。

### 任务 5：方案审批、失败处理和历史保留

- 修改 `api.ts`、`approval.ts`、`store.ts`、`finding-approval-state.ts`、`vcs.ts`。
- 审批显式传入方案和 patch 选择，不能临时改写 currentRevision 来伪装选中方案。所有重读和门禁后核对都绑定同一选择。
- 验证失败仅还原并记录，禁止 AI 修复分支；记录提交失败或结果不明沿用恢复纪律。
- 新问题批准保留 patch，Git/SVN 均可正确派生业务提交；旧已归档且缺失 patch 的记录仍可读。
- 验收：选 001 不会应用最新 002；门禁失败时即使 autoFixOnFailure=true Runner 调用数也为零；状态、记录和回退一致。
- 同步修改 `runner.ts::RunnerRequest/buildFixPrompt`、`api-fix-session.ts::fixPrompt`、`api-readmodels.ts::fixPrompt`、`api-writers.ts::validateNewRevision` 和 Fixer 系统模板。所有反馈、Rebase 与应用辅助入口均显式绑定方案和补丁；新补丁号来自全目录账本，保留其他方案和历史，禁止将 v3 重写为 schema1。

### 任务 6：人的处置、复发与中央协议

- 修改 `finding-decisions.ts`、`audit-history.ts`、`api-readmodels.ts`、`api-writers.ts`、共享协议及中央能力适配。
- 新问题的人工处置写同一 review.md，不再写外置处置文件；复发沿用原问题，外部完成待复核。
- 批准 payload 显式方案身份；新格式写入由双方能力协商，旧端不支持时明确拒绝，不静默降级。

### 任务 7：本地与中央界面

- 修改 `packages/dsh-plugin/src/client/client.ts` 与 `apps/web/src/App.tsx` 及必要协议类型。
- 在同一问题展示文字方案、零到两个可选 patch、各方案当前差异、历史补丁、待人工失败与外部完成反馈。
- 人工批准绑定当前所选方案；页面刷新或问题更新后旧选择不可继续提交。

### 任务 8：独立复审与完整验证

- 对照以上 17 项逐项核查，不只统计文件或匹配提示词字符串。
- 新增行为测试覆盖大文件实际工具读取、审查不应用、跨轮保留、方案选择、失败还原与记录、Git/SVN 保留历史、中央新旧版本和两端界面。
- 既有断言若因新规范必须改变，逐项说明“跟随规范收紧”，不减少测试或放宽结论。
- 运行 `npm run typecheck`、`npm run build`、`node --test --test-concurrency=1 --test-reporter=tap tests/*.test.mjs`。
- 按 AGENTS 做独立对抗性审查，逐条复核并修正成立的问题。完成后中文提交到任务分支，不合并、不 push、不改版本号。

## 自审结论与防止副作用

- 新格式在原路径中升级，避免新增并行存储和多份当前状态；旧记录不自动批量重写。
- 复用已有 VCS 与事务机制，避免另造提交和恢复框架。
- 读取范围、报告范围、写入权限分别处理，防止再次把“独立复核”实现成“没有工具”。
- 审查检查不得偷偷应用补丁，生成与收尾两条路径都须覆盖。
- 保留 patch 必须同时修正业务提交派生；方案选择必须从协议贯穿到实际应用。
- 不新增自动门禁失败修复或额外成功复核；不扩大推送与发布授权。
- 中央混合版本须通过能力和严格 payload 核验，防止旧端误解释新记录。
- 独立方案复审补入：反馈、Rebase、修复会话、导出修复提示词及新版本校验均需携带方案身份，避免修复 Agent误用最高补丁编号。阶段工具事件流改为流式处理，不使用最终结果的大小上限判断整个 Agent Loop。

## 实施复审补充

1. 修复 record_revision 与 patch 编号混用：两端差异只比较同方案的 patch 历史，读请求按方案追踪最新补丁，写请求仍绑定明确补丁和原 guard。
2. 行内评论保留 option_id/patch_id，跨方案不混用；反馈提示保留绑定身份。
3. 交互式会话/导出反馈通过既有 candidate/finalize 的 schema3 分支收尾，复用原校验及提交分类，只提交 review.md 与新增 patch。
4. 定时审查的文件变化集合接受已封存的问题更新、历史 patch 和证据子目录；封存外变化仍拒绝。
5. 主 DSH 会话通过原生逐会话 resolver 约束写根；审查子 Agent 继承同 cwd。对不继承 DSH 权限的 subagent_oar 与 worktree 写工具使用公开 tools.guard 拒绝，保留普通读取与受控阶段。
6. 工具守卫注册在 Agent scope 而非插件 scope，未知停止时不会随插件卸载提前失效；新 Agent 对象恢复原 session 时重新注册，disposed 后释放引用。真实 Cordis/ToolRuntime 独立探针已验证生命周期。
7. schema3 兼容迁移保留旧人类决定、修复线索与批准记录；旧版已删除 patch 从对应 VCS 历史恢复，不虚构补丁。
8. 避免新模块循环依赖：问题数据校验直接依赖底层路径校验，原 invariants API 继续兼容导出。
