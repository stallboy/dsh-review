# 中央定时审查实施计划

> **任务来源**: 用户确认由中央服务替代本地定时器，各项目按指定时刻触发，遇忙最多等待 30 分钟。
> **任务内容**: 实现无人值守的历史复查、全仓扫描、校验归档及交付。
> **参考文档**:
> - `SPEC.md` — 档案、有效观察、审查互斥、中央任务与远端交付契约。
> - `docs/plans/2026-11-16-central-web-discussion.md` — 已确定复查上轮后再做全量审查。
> - `docs/superpowers/specs/2026-11-16-central-review-web-design.md` — 中央服务和执行节点的职责边界。
> **生成日期**: 2026-11-18

中央以 SQLite 保存项目的定时配置，节点轮询时由中央判定到期任务并持久化派发。选择该方式是因为执行需要在线节点，节点已有轮询、确认和恢复链路。固定时刻单次尝试在临时繁忙时容易错过整轮，节点本地定时器则会绕过中央的占用管理和任务追踪。

## 约定

- 每个项目默认关闭，用户配置每日 `HH:mm` 和 IANA 时区。开始时刻含在等待期内，满 30 分钟即截止。跨午夜仍按计划开始的本地日期去重。夏令时重复时刻采用首次，不存在的本地时刻跳过当日。
- 中央在线、兼容、启用并有自动审查能力的节点空闲时派发，既有手动任务优先。命令携带 `scheduledAudit: { scheduledAt, expiresAt }`，由中央构造。项目和本地日期决定幂等键。截止或关闭时尚未受理的命令可由中央结束，已受理任务遵循现有取消、收尾及恢复规则。
- 自动命令使用审查专用系统身份，候选按 `reviewers.yml` 路由，使用配置时的登录审核身份兜底。节点以进程 Runner 执行，共用仓库锁及交付链路。
- 节点从同步后的同一共享基线读取上份已提交全仓档案、上轮已批准候选及有效未闭合的 finding。先提交结构化复查结论，再全量扫描。已证实消失才采用原 ID 写入 `resolved`，证实仍在才记录新观察，未核实保留旧状态。空历史直接全量扫描。

## 实施与验收

1. **中央调度和协议。** `packages/protocol/src/index.ts` 定义可选计划信封和能力声明。`apps/server/src/audit-schedule.ts` 管理时区、配置及状态，`commands.ts` 在节点轮询时先派发现有指令，`app.ts` 提供项目详情和 `PUT /api/v1/projects/:projectId/audit-schedule`。用现有可注入时钟测试时限、离线/繁忙、跨午夜、重启去重和到期未受理。
2. **节点与审查档案。** `managed-node.ts` 尊重确认后的命令状态，`managed-operations.ts` 将受信触发信息传入本地执行。`host/api-audit.ts` 和 `host/auditor.ts` 在仓库锁和租约下同步、复查、扫描及收尾。用临时 Git 仓库和测试 Runner 验证触发值、前驱档案、稳定 finding ID、未核实项及实际共享产物。
3. **Web 与本地迁移。** `apps/web/src/App.tsx` 与 `api.ts` 加入定时设置、上轮原因和下次时间。移除本地定时器、设置、所有调用点，替换绑定旧定时器的测试，保留手动审查的租约和 Owner 路由覆盖。更新 `SPEC.md`、`README.md` 与中央用户指南。
4. **联调。** 先跑定向回归，再运行 `npm run typecheck`、`npm run build` 和 `node --test --test-concurrency=1 --test-reporter=tap tests/*.test.mjs`，完成独立契约审查后提交任务分支。
